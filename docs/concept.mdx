## Overview

MPF Hook turns the priority fee (the one lever MEV bots must pull to win block ordering) into a signal for pricing risk. Aggressive bidders pay a proportionally higher swap fee, and liquidity providers collect it.

## Problem the hook solves

MEV bots make money by cutting in line. Front-running and sandwich attacks only work if the bot's transaction lands right before a target trade.

The only lever a user has to influence ordering inside a block is the priority fee. So bots bid it up, aggressively.

Ordinary users pay more for the same trade, and liquidity providers absorb the risk. The pool itself gets nothing out of it.

## How it solves it

The hook doesn't look at prices or trade sizes. It looks at how the user _behaves_, specifically at the priority fee they attach to their transaction:

```text
GasPrice = BaseFee + PriorityFee
```

Base Fee is set by the protocol. It's the same for every transaction in a block and reflects network congestion, not user intent.

Priority Fee is different. The user picks it to buy earlier inclusion, and it's exactly the knob front-runners turn to outbid their target.

So the hook keeps a continuously updated median of recent priority fees. When an incoming fee sits well above the median, it's flagged as aggressive and charged a proportionally higher swap fee.

That extra fee goes back to liquidity providers, compensating them for the MEV risk they carry.

## Extra advantage

One hook instance isn't locked to a single pool. It can serve dozens or hundreds of pools at once, all feeding into the same shared TWAP instead of each keeping its own median.

That matters most for small pools. A thinly-traded pool doesn't see enough transactions on its own to build a reliable priority-fee baseline, so its median stays noisy and easy to game.

Pooling the signal across many pools fixes that. Low-liquidity hooks piggyback on the data generated by busy pools, and get a well-calibrated defense they could never produce in isolation.

## FrugalMedianLibrary: the median, on a budget

The hook uses a **frugal streaming median**, an approximation that updates with every new value, no history and no sorting required. State is just three variables: `approxMedian`, `step`, and `positive`.

<Frame>
  ```mermaid
  flowchart TD
  Start(["New value comes in"]) --> Cmp{"newNumber vs approxMedian"}

  Cmp -- "bigger" --> Up1["adjust step based on direction"]
  Up1 --> Up2["approxMedian += step (or +1 if step ≤ 0)"]
  Up2 --> Up3{"overshot? approxMedian > newNumber"}
  Up3 -- yes --> Up4["snap back: approxMedian = newNumber<br/>step corrected"]
  Up3 -- no --> Up5["fine as is"]
  Up4 --> Up6{"was going down, step > 1?"}
  Up5 --> Up6
  Up6 -- yes --> Up7["reset step to 1"]
  Up6 -- no --> Up8["positive = true"]
  Up7 --> Up8

  Cmp -- "smaller" --> Dn1["adjust step based on direction"]
  Dn1 --> Dn2["approxMedian -= step (or -1 if step ≤ 0)"]
  Dn2 --> Dn3{"overshot? approxMedian < newNumber"}
  Dn3 -- yes --> Dn4["snap back: approxMedian = newNumber<br/>step corrected"]
  Dn3 -- no --> Dn5["fine as is"]
  Dn4 --> Dn6{"was going up, step > 1?"}
  Dn5 --> Dn6
  Dn6 -- yes --> Dn7["reset step to 1"]
  Dn6 -- no --> Dn8["positive = false"]
  Dn7 --> Dn8

  Cmp -- "equal" --> NoOp["nothing to do"]
  ```
</Frame>

### The gist of it

<Steps>
  <Step title="New value is above the estimate">
    Push the estimate up by `step` (at least 1). If that overshoots the new value, snap back exactly to it and trim `step` by the overshoot amount.
  </Step>
  <Step title="New value is below the estimate">
    Same thing, mirrored, push down instead.
  </Step>
  <Step title="Direction flips">
    If the new move contradicts the last one (tracked via `positive`), `step` resets to 1. This damps oscillation so the estimate doesn't overshoot wildly when the trend reverses.
  </Step>
  <Step title="Direction confirmed">
    If it's moving the same way as before, `step` grows via `stepIncrement()`, which in this implementation always just returns `1`, so growth is linear rather than accelerating (a simplified version of the classic algorithm).
  </Step>
</Steps>

<Note>
  This isn't an exact median, it's a fast approximation that drifts toward the real median over time. It can lag a bit behind sudden shifts in the distribution of values.
</Note>
