## Problem the hook solves

MEV bots make money by cutting in line. Front-running and sandwich attacks only work if the bot's transaction lands right before a target trade.

The only lever a user has to influence ordering inside a block is the priority fee. So bots bid it up, aggressively.

Ordinary users pay more for the same trade, and liquidity providers absorb the risk. The pool itself gets nothing out of it.

## How it solves it

The hook doesn't look at prices or trade sizes. It looks at how the user _behaves_, specifically at the priority fee they attach to their transaction:

```text
GasPrice = BaseFee + PriorityFee
```

Base Fee is set by the protocol. It's the same for every transaction in a block and reflects network congestion, not user intent.

Priority Fee is different. The user picks it to buy earlier inclusion, and it's exactly the knob front-runners turn to outbid their target.

So the hook keeps a continuously updated median of recent priority fees. When an incoming fee sits well above the median, it's flagged as aggressive and charged a proportionally higher swap fee.

That extra fee goes back to liquidity providers, compensating them for the MEV risk they carry.

## Extra advantage

One hook instance isn't locked to a single pool. It can serve dozens or hundreds of pools at once, all feeding into the same shared TWAP instead of each keeping its own median.

That matters most for small pools. A thinly-traded pool doesn't see enough transactions on its own to build a reliable priority-fee baseline, so its median stays noisy and easy to game.

Pooling the signal across many pools fixes that. Low-liquidity hooks piggyback on the data generated by busy pools, and get a well-calibrated defense they could never produce in isolation.
